# .91 RAM lifetimes and flash-enabling audit

2026-10-28. Frozen baseline: `build/flash-audit-91/baseline/source`, including the uncommitted .91 hold-delay and worker-hardening changes. This audit changes no production firmware, assets, installer, version, existing reports or Git state. All experiments, patches, generated output and test executables are private under `build/flash-audit-91/ram/`. No flashing, commits, pushes, PRs or delegation occurred.

**Result:** no large safe RAM recovery was established. The old `proj_v3_tmp` proposal is already implemented by direct conversion and provides **zero new bytes** on .91. A measured runtime-layout experiment recovers **80 B main RAM but costs 2,256 B flash**, so reject it. Existing free RAM can buy a small, byte-exact startup-literal reduction: **156 B flash using 512 B main RAM**, or **120 B using 400 B pool**. The actual combined link saves **236 B**, not their 276 B sum. These are optional RAM-for-flash trades, not RAM savings; the combination leaves only 48 B pool above the retained reserve and is not a comfortable platform for further work.

### Legacy conversion: resolve the stale proposal

`project.c` retains types for all six formats, but formats 1/2 convert directly into the final destination through the existing old-field helpers; format 3 is read directly from the import source. `proj_import` dispatches after record validation. There is no `proj_v3_tmp` in source or linked symbols. The earlier architectural report's **up to 2,584 B** proposal was superseded by the integrated direct conversion documented in OPTIMIZATION and the ambient RAM audit. The measured remaining `proj_tmp` is **3,840 B**, not that removed 2,584 B object. Claiming it again would double-count an implemented optimization.

### Storage alias counterexample, executed against actual .91 code

`ram/alias-counterexample.c` includes the private frozen `tests/storage_test.c` and actual `storage.c`, preserving its NOR model and XIP support. Built with assertions, `-O2 -fwrapv -fno-strict-aliasing`, and UBSan with no recovery, it demonstrates:

1. Save a valid 3,816-byte old autosave.
2. Fill `main_scratch.st` with a different intended autosave and pass it as `st_save`'s source.
3. The call reports success, but reloading returns **the old payload**, not the intended new one.

`st_save3` calls `st_current` before copying its source. `st_current` validates the old body into `st_buf`, which is `main_scratch.st`, destroying the new source. CRC/commit validation cannot catch this: it faithfully commits the wrong bytes. The oracle also confirms that `st_current` overwrites a live scratch-backed project on a read path. See `alias-counterexample.log`.

Changing only saves to XIP selection is insufficient. `autosave_resume` holds `q=&autosave_buf`, calls `proj_apply(q,1)`, then `snapshot_resume(q)`, and subsequently reads `q->sel`. `snapshot_resume` calls `snapshot_read`, which validates settings through `st_current` before matching the working snapshot to `p->sum`. An aliased q is overwritten before that comparison. `snapshot_prepare` also captures autosave while settings staging is active. A future redesign must define source lifetime through every success/error/readback path, not merely prove self-copy in `st_load`.

### USB, UI and OTA retention

Editor backup LIST captures the working project in `ED_BK_RAW=&proj_tmp`; later GET requests read slices of that same snapshot. PUT accumulates a multi-request object before commit. Thus this storage outlives one main-loop callback. Between requests, visualizer/UI work can legitimately overwrite `main_scratch`. Editor upload decoding already uses `main_scratch.smp`, distinct from backup staging. OTA frame decoding uses `main_scratch.dec`, while `OTA_STAGE_RAM` points at `proj_tmp`; OTA reads must preserve previously staged loader/package data while decoding later replies. These are simultaneously required roles, even when the main loop serializes individual callbacks.

TIMER5 can interrupt rendering and service the USB audio consumer; normal USB polling is deferred out of nested audio. Audio sequencing may capture pattern undo. Core 1 owns render-unit scratch until the worker barrier, including timeout handling. A main-loop scratch loan cannot assume its caller runs without preemption. No IRQ suppression, worker/barrier change, overload-policy relaxation or new lock is part of the measured candidates.

### Undo: logical exclusivity is insufficient for a ready patch

Whole-project undo availability requires matching `undo_sess` and `undo_revision` and `!undo.valid`. Pattern `undo_mark` increments revision before snapshotting; later clearing `undo.valid` cannot resurrect old project history. This suggests sharing some payload bytes, **not proof of an implementable 716 B saving**. The valid flags, revision/session and undone state must remain separate from overwritten payload. Project capture/byte exchange, pattern recording marks and adoption clearing require ownership transitions that survive preemption. A union also needs a type declaration available before `seq.c`, while `project_t` is currently declared later, with independent PROJ_HOST/test inclusion paths. Casting a fixed byte buffer is not an acceptable substitute for a typed/aligned lifetime design. No such patch is measured or recommended here.

## Engine arena and cold metadata opportunities

The present arena already holds DRAWBAR's seven-control cache and GRAIN's half-segment checkpoints. PHYS sets its 8,592-byte per-part extent. Reducing GRAIN checkpoints changes a performance optimization, not dead capacity; shrinking the arena below PHYS needs a model/quality redesign and is excluded. Arena claims clear old engine state, and engine switching waits for the old voices to fade/retire. Slots for three parts cannot be globally overlaid because rendering and releases coexist, including two-core execution.

**Unmeasured follow-up:** put FM6's 600 B derived cache into its existing arena slack if target ABI proves the enlarged FM6 member still fits. There is a specific semantic trap: `fm6_sync` calls `fm6_lfo_reset` on a real cache miss. Today `fm6_eff` survives arena eviction. Clearing it on every arena claim would create new cache misses and reset the external LFO when returning from PHYS/GRAIN/DRAWBAR, changing sound. A correct design may retain generation/seven-macro keys outside the arena, rebuild only the evicted derived bytes without an extra LFO reset, and distinguish eviction from actual patch changes. Those retained keys, new branches, address loads and claim-before-access calls consume RAM/code/runtime. `fm6_patch`, LFO phase and patch publication must retain their existing lifetimes. This is a better bounded next experiment than treating all control state as disposable, but **no 600 B net recovery or flash combination is claimed**.

Boot-restored numeric tables, zones, presets, names and font data remain live after initialization and serve UI/audio pointers. Only their input scratch is boot-only; that scratch already becomes ordinary project staging. Earlier preset relocation transfers 6,156 B between regions and can add alignment bytes; it does not save total RAM and cannot fit current 804 B main margin. Earlier cold-state initialization regressions remain rejected, not revived by this report. Runtime sample packing and executable overlays are outside these candidates.

Warm-reset state is especially excluded: `.noinit` is 15,472 B, including retained project slots and `.noinit.c1bar` worker quarantine. The eight-byte bar follows existing records and must survive warm resets. The NOINIT region is 15,696 B, leaving only 224 B; these bytes are not a cold conversion allocation. No relocation or reuse of boot_info, mailbox, crash/update records, stack guards or retained project bytes is proposed.

* Actual target proof checks **1,405 complete original objects**, every final relocated address, real C startup restoration three times, byte equality and destination guard bytes under UBSan. * Normal target region checks pass: 925 call-free RAM-text instructions, 160-byte core-1 loop, 6,216-byte persistent scratch, register-access policy and all existing DSP loop budgets. No budget files or assertions were weakened.

For rejected track reordering, the actual project test passes under UBSan (96 output lines), including legacy records, byte-level storage, complete project-load undo/redo, later-edit invalidation and recording supersession. This is not full UI/audio/dual-core qualification; rejection on image size makes broader integration testing unnecessary. No timing/stack or universal behavioral equivalence is claimed for that patch.

The exact byte/relocation restoration proof is the relevant behavior oracle for these data-placement changes; a new native audio golden pass would not execute target literal pooling.

Hardware gates for any chosen literal trade: cold boot/watchdog and ROM recovery behavior; stack high-water including nested IRQ/core-1 execution; full UI/USB backup/restore and update/recovery smoke checks; long mixed-engine/LOFI playback under the unchanged overload guard. Firmware listening/deadlines were not measured on this shared host. Re-link and revalidate any eventual integration because even the two measured one-line alternatives interact. No multi-KiB RAM or combined flash win is promised by the unmeasured designs above.
