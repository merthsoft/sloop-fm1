# Ambient headroom: RAM buffers and lifetimes

Audit date: 2026-10-24. Production baseline: MerthSloop 2.8.0.58. Experiments use a frozen copy of the **current working files**, including the integrated uncommitted changes at capture time, not HEAD. All experiment sources, generated headers, binaries, logs and patches are under `build/headroom-ambient/ram-buffers/`. No production source, shared generated output, installer, version or Git ref was changed by this audit.

**Recommend the FFT-only patch: recover 1,024 bytes of audio pool with zero linked flash cost and no other RAM increase.** There is no substantiated large dead audio reservation. Sequential audio scratch can recover 768 main RAM bytes, but the measured implementation increases flash enough to exceed the current slot; do not integrate that version.

### Actual block routing and barrier

`fx.c:mix_block` runs events, starts optional core-1 units, renders core-0 units, joins using `cpu1_wait`, handles timeout fallback and merges all five accumulators. Only then does it run:

1. `texture_mix`: produces temporary stereo bed, adds it to dry mix, returns with no saved pointer to its arrays.
2. `punch_freeze_feed`: may add dry signal to the reverb send; it does not consume old texture scratch.
3. `fx_buses`: reads independent chorus/delay/reverb send arrays, advances all histories, writes wet stereo **and separate reverb-only stereo**.
4. Wet summing: consumes all wet samples into dry stereo before the next stage.
5. Dust, LOFI, `punch_process`, master filter: punch kills use `kl/kr`; FREEZE additionally reads retained `rev_l/r`.
6. DAC and optional FULL USB preprocessing: four output rows coexist until their separate limiters/output copies finish. `usb_out` survives for `audio_block` afterward.

The four-row experiment overlays only stages 1/3/5/6. It leaves accumulators, per-core render scratch, persistent histories, reverb-only returns and asynchronous outputs separate. This is exclusion established by call order and the core barrier, not UI page selection. It requires no allocation, locks, copying, decoder or extra clearing in the proposed target code. Nevertheless, compiler global-layout changes increased linked flash; source simplicity does not establish target cost.

## Ranked recommendations

### 1. Reuse the consumed waveform for FFT imaginary components

Patch: `build/headroom-ambient/ram-buffers/fft.patch`, one production file, `firmware/src/ui_vis.c`. Replace the standalone `vis_im` array with `#define vis_im vis_frame.scope.l`.

In the first FFT loop each iteration reads `vis_l[i]`, writes its windowed real value to `vis_re[i]` (the separate `main_scratch.snap`), then writes imaginary zero to that same waveform element. No later iteration reads a previous waveform element. The remaining FFT and band loops use only real/imaginary arrays. SPECTRUM/SPECTROGRAM drawings consume bars or spectrogram history, not the destroyed waveform. OSCILLOSCOPE does not invoke this FFT. Every non-TRAILS update refills the waveform before use; entering TRAILS clears its union member. `vis_update` completes before canvas rendering and has no callback into audio using these arrays. Audio interrupts touch the independent scope producer, not `vis_frame`.

Measured linked result is **1,024 B less pool**, no main/low increase and **zero total image delta**. Named `vis_fft` falls from 300 to 294 bytes, but load image alignment absorbs that six-byte function reduction; do not advertise it as flash savings. No audio function, audio loop, runtime sample format or effect combination changes. Host FFT work remains the same loops and arithmetic; target FFT code shrinks, but physical UI timing/cache behavior is unmeasured. Upstream burden is low: one local allocation alias and a lifetime comment. Future drawing code must not expect the waveform to survive spectral analysis.

### 2. Retain the proven audio-scratch lifetime map, defer its current patch

`scratch.patch` has a measured **768 B main RAM recovery**, with zero low/pool change, but costs **1,168 B flash** and no longer fits .58. The combined experiment costs 1,152 B flash. `scratch-lite.patch` saves only 512 B RAM and costs 1,248 B flash. Both are rejected for integration now; do not call the proposed overlay free CPU/flash merely because it introduces no arithmetic. They are concrete starting points if a later toolchain/layout change makes RAM more valuable than code capacity. Upstream burden is medium: several audio stages acquire a shared lifetime contract, and future parallel work must honor the join.

### 3. Larger capacity requires an explicit architectural change

The 131,072-byte delay and 65,536-byte punch histories dominate audio pool use and remain simultaneously live. Shrinking them reduces supported delay/replay length; repacking them changes precision or adds audio-path work. Those are feature/quality decisions excluded here. The 59,520-byte canvas is a larger non-audio target, but tiled rendering would require a complete caller and LCD DMA ownership redesign, framebuffer parity and target measurements; no recovered byte claim is made. Moving persistent pool objects to spare main RAM transfers budget between regions without reducing total RAM, and is not counted as savings.

## Correctness and instrumentation

Validation logs and exact commands are retained alongside the patches. Host compiler is pinned Zig 0.13.0 (`zig cc -O2 -UNDEBUG`, host includes, `-lm -pthread`). Host timings are not target timings.

- A standalone oracle executes the original FFT and destructive-waveform version on **10,000 inputs**, including silence, both full-scale constants, alternating extremes and deterministic random inputs. **10,240,000 real/imaginary component comparisons** agree exactly. See `fft-oracle/result.log`; oracle generation uses the frozen original function.
- Baseline and combined candidate host copies exercise the actual DSP/UI, preserving assertions. **All 16 executions pass** (eight per copy: three scheduling modes of the split suite plus five focused suites). The combined candidate includes the recommended FFT change and the more invasive scratch overlay, providing a stronger interference check than FFT-only audio tests.
- The dual-core suite covers seven scenes and all eleven unit masks, in deferred single-thread mode, actual pthread mode with delayed scheduling, and lost-job/timeout fallback. Scenes include three simultaneous FM6 parts; PHYS layout/model changes; GRAIN/DRAWBAR with sends; drum slicer/filter; texture, inserts, freeze and simultaneous preset fades; sample cache and live modulation.
- Focused suites exercise all 27 punch effects and exact dry restoration, 30-second freeze, spring capture/hold/release and the wide freeze oracle (41,472 stereo samples plus 55,232 large-product checks for each spring sign), every reverb model's tail/damping/frozen live switching, sampler coloration and full actual-UI behavior with 20,000-frame fuzz. **All 79 captured framebuffers match byte for byte** between baseline and combined. See `validation.json` and per-copy `results/` logs.
- A separate host-only instrumentation pass fills all four shared scratch rows with `0xA5` immediately before texture, buses, punch and master output preparation, and aborts if a core-1 job is still pending at any boundary. The seven-scene / eleven-mask split suite passes in deferred, delayed pthread and timeout modes. **Every printed output hash is identical to the original unmodified baseline**, with no pending-job assertion. This tests independence from prior stage/block contents, while freeze returns and persistent histories remain outside the overlay. `poison-validation.json` and `hostcombined/results/poison*.log` retain the evidence. The instrumentation is absent from target candidates. Dynamic coverage is the stated scenes and transitions; arbitrary future effect code still needs the explicit stage-lifetime contract.
- `source/results/fft-normal/checks.txt` and final target budget/inlining logs document normal-slot placement, 925 call-free RAM-text instructions, 60-byte core-1 loop and unchanged persistent scratch. The oversized scratch links have the expected app-slot errors and are not successful release candidates.

No hardware is available for stack high-water, nested ISR deadline, external LCD DMA behavior, playback listening or boot/watchdog measurements. The recommended change does not alter audio code or audio ownership; these limits must still be retained when assessing broader scratch changes.
